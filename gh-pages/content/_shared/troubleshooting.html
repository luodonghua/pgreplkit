Troubleshooting

The most common problems, what causes them, and how to fix them.

Subscription is created but no data arrives

  • Check connectivity first. The subscriber makes an outbound connection to the publisher on port 5432. From the target host:
    bash — from the TARGET host 
    psql "host=SOURCE_HOST port=5432 user=repluser dbname=appdb" -c "select 1"
    If this fails, it is a network/firewall/security-group or pg_hba.conf issue, not a replication issue.
  • Confirm the subscription is enabled:
    psql — on TARGET 
    SELECT subname, subenabled FROM pg_subscription;
-- if subenabled = f:
ALTER SUBSCRIPTION sub_app ENABLE;
  • Look at the target server log. The logical apply worker writes the real reason there (permission denied, publication missing, connection refused).

Error: "cannot update/delete table … does not have a replica identity and publishes updates"

This fires on the SOURCE and blocks your application A table is part of a publication that publishes updates/deletes but has no primary key or REPLICA IDENTITY. The publisher refuses the UPDATE/DELETE outright — this is a live-application outage, not just a replication issue. Fix it by giving the table an identity:
psql — on SOURCE 
ALTER TABLE my_table REPLICA IDENTITY USING INDEX my_unique_idx;  -- preferred
-- or, if there is no suitable unique index:
ALTER TABLE my_table REPLICA IDENTITY FULL;
Run the row-identity pre-flight query (in Prerequisites) to find every such table before you start.

Error: "logical replication target relation … is missing replicated column"

The target table exists but lacks a column the publisher is sending. The target schema must be a superset of the published columns. Add the missing column on the target to match the source, then the apply worker resumes on its next retry. This is why you pre-create the target schema from the source with pg_dump --schema-only and keep DDL in sync.

Error: "cannot add relation … to publication"

You tried to publish something that isn't an ordinary or partitioned table — an unlogged table, temporary table, view, materialized view, foreign table, or system table. None of these can be replicated. Remove it from the publication; for unlogged tables that must move, convert with ALTER TABLE … SET LOGGED first.

Error: "publication does not exist"

The subscription was created (or the slot started replaying) before the publication existed on the source. Always create the publication first, then the slot/subscription. Create the missing publication on the source and the worker will recover on its next retry.

Duplicate key / unique constraint violations on the target

Almost always a seeding mistake This means rows that were already loaded into the target are being replayed again by the stream. It happens when a manual (pg_dump) seed was not taken at the slot's exported snapshot, so the slot replays WAL from before your dump. Re-seed using the exported-snapshot procedure (dump exactly at the slot's snapshot, then subscribe with copy_data = false).

Error: "could not create replication slot ... all slots are in use"

Raise max_replication_slots and max_wal_senders on the source (and max_logical_replication_workers / max_worker_processes on the target), then restart. Each subscription needs one slot and at least one worker.

Replication was fine, then broke with wal_status = lost

The source recycled WAL the target still needed (target fell too far behind, or a bounded max_slot_wal_keep_size was too small). There is no way to resume — drop the subscription and slot and re-seed. Prevent it by keeping the target caught up and monitoring lag.

Row counts don't match after the copy

  • Tables without a primary key or REPLICA IDENTITY cannot replicate UPDATE/DELETE. Add a PK, or set ALTER TABLE t REPLICA IDENTITY FULL; before starting.
  • The target schema was created after the publication started, so some tables were never added. Re-run ALTER SUBSCRIPTION ... REFRESH PUBLICATION; on the target.
  • Sequences are never replicated — their values will differ until you sync them at cutover (see the cutover step).

Large initial copy is slow or stalls the source

The built-in copy holds a read on the source. For very large datasets prefer a physical seed (RDS snapshot restore or Aurora fast clone) when source and target are the same platform and major version, or a parallel pg_dump seed with the exported-snapshot procedure.

General debugging order 1) target server log → 2) pg_stat_subscription_stats.apply_error_count → 3) network test from the target → 4) publication/slot existence on the source. That order finds the cause fastest.

Error reference: cause and fix

Common errors the PostgreSQL server raises, mapped to what causes them and how to avoid them. The ones marked verified were reproduced on PostgreSQL 16.

Error (paraphrased)WhenCause & how to prevent it
cannot update/delete table … does not have a replica identity and publishes updates verified App write on SOURCE Table is in a publication but has no PK/replica identity. Run the row-identity pre-flight and set a PK or REPLICA IDENTITY before creating the publication.
cannot add relation … to publication (unlogged/temp/system/view) verified CREATE/ALTER PUBLICATION Only ordinary + partitioned tables can be published. Don't include unlogged, temporary, system, view, materialized-view or foreign-table objects.
cannot use column list … in publications containing FOR TABLES IN SCHEMA verified CREATE/ALTER PUBLICATION You can't mix a per-table column list with a whole-schema publication. Use one approach: schema-level, or explicit tables with column lists.
logical decoding must be enabled to publish logical changes / wal_level is insufficient CREATE SUBSCRIPTION / slot wal_level not logical on the source (or rds.logical_replication not set). See the configuration parameters in Prerequisites; a restart is required.
logical replication target relation "…" does not exist Apply on SUBSCRIBER Target table/schema missing. Pre-create the schema; re-run ALTER SUBSCRIPTION … REFRESH PUBLICATION if you added tables later.
… is missing replicated column: … Apply on SUBSCRIBER The target table lacks a column the publisher sends. Keep the target schema a superset of the published columns.
… has incompatible generated column: … Apply on SUBSCRIBER A column is stored/normal on the publisher but a generated column on the subscriber (or vice versa). Make the column definitions match.
publisher did not send replica identity column expected by … target relation Apply on SUBSCRIBER The publisher's replica identity doesn't cover what the subscriber needs. Align replica identity (and, if you use a column list, include the identity columns).
cannot use relation "…" as logical replication target Apply on SUBSCRIBER The target object is not a plain/partitioned table. Only tables can be subscription targets.
The single most important habit Run the row-identity pre-flight on the source, and make the target schema an exact superset of the published tables/columns, before creating the publication and subscription. Those two habits prevent the large majority of the errors in this table.
