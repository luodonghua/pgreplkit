Set up replication — pg_dump / pg_restore seed

Here you load the existing data yourself with pg_dump/pg_restore (which you can parallelize and tune), then attach logical replication with copy_data = false so it only streams changes. This is version-independent and works on every platform.

The one rule that makes this exactly-once You must take the dump at the exact point in time that the replication slot starts from. If you dump at any other moment, the stream will either miss rows (dump too early) or re-apply rows already in the dump, causing duplicate-key errors (dump too late). PostgreSQL gives you that exact point as an exported snapshot when you create the slot — use it with pg_dump --snapshot.
1 Create the publication on the SOURCE
psql — on SOURCE 
-- specific tables:
CREATE PUBLICATION pub_app FOR TABLE customers, orders;
-- or entire schema (PG 15+):
-- CREATE PUBLICATION pub_app FOR TABLES IN SCHEMA app;
Create the publication before the slot. The slot replays from its start point, and the publication must already exist at that point or the apply worker fails with "publication does not exist".
2 Create the slot and capture its exported snapshot

Open a special replication connection and create the logical slot with EXPORT_SNAPSHOT. It returns a snapshot name. Keep this session open — the snapshot is only valid while the session that created it is alive.

psql — on SOURCE, replication connection (leave open!) 
psql "host=SOURCE_HOST port=5432 user=repluser dbname=appdb replication=database"

-- inside that session:
CREATE_REPLICATION_SLOT sub_app LOGICAL pgoutput EXPORT_SNAPSHOT;
--  slot_name | consistent_point | snapshot_name       | output_plugin
--  sub_app   | 0/1D6C6B8        | 00000004-0000009F-1 | pgoutput
-- ^ note the snapshot_name. DO NOT close this psql yet.
Creating the slot fixes the resume point on the source's timeline and pins the WAL from there so nothing after it is lost. The exported snapshot is that same instant, expressed as something pg_dump can read from.
3 Dump at the snapshot and restore to the TARGET

In a second terminal, dump using --snapshot with the name from step 2, then restore into the target. The session from step 2 must stay open for the whole dump.

bash — second terminal 
SNAP='00000004-0000009F-1'   # from step 2

# schema + data, exactly at the slot's start point
pg_dump "host=SOURCE_HOST port=5432 user=repluser dbname=appdb" \
        --snapshot="$SNAP" -Fc -f appdb.dump

# restore into the target (create the DB/roles first if needed)
pg_restore -d "host=TARGET_HOST port=5432 user=repluser dbname=appdb" \
        --no-owner --jobs=4 appdb.dump

--jobs=4 restores several tables in parallel. Tune to your target's CPU/IO.

4 Close the replication session

Once the dump has finished reading, you can close the psql session from step 2 (type \q). The snapshot is no longer needed; the slot remains.

5 Attach the subscription (no copy) on the TARGET

Create the subscription reusing the slot you already made, with copy_data = false and create_slot = false. It streams changes from exactly where the dump ended.

psql — on TARGET 
CREATE SUBSCRIPTION sub_app
  CONNECTION 'host=SOURCE_HOST port=5432 user=repluser password=SECRET dbname=appdb'
  PUBLICATION pub_app
  WITH (
    copy_data    = false,   -- data is already loaded by pg_restore
    create_slot  = false,   -- reuse the slot from step 2
    enabled      = true,
    slot_name    = 'sub_app'
  );
Because the dump was taken at the slot's snapshot, the first change the stream applies is the very next one after the dump — no gap, no overlap. This is the exactly-once boundary.
