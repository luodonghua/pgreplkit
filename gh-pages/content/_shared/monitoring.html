Monitor progress

Replication has two phases you watch differently: the initial copy (existing rows being loaded) and streaming (live changes flowing). The queries below tell you exactly where you are. Run the source queries on the publisher and the target queries on the subscriber.

1. On the TARGET: is the initial copy finished?

Each table goes through states: i = initializing, d = copying data, s = synchronized (finishing), r = ready (streaming). When every row shows r, the initial copy is complete and the table is live.

psql — on TARGET, inside the replicated database 
SELECT srsubstate AS state, count(*) AS tables
FROM pg_subscription_rel
GROUP BY 1
ORDER BY 1;
-- state 'r' for every table  = initial copy done, now streaming

2. On the SOURCE: how far behind is the target (lag)?

Lag is the volume of WAL (write-ahead log) the source has generated that the target has not yet confirmed applying. During a quiet period it should fall to 0. A steadily growing lag means the subscriber can't keep up (check network, target CPU/IO).

psql — on SOURCE 
SELECT
  slot_name,
  active,                                  -- t = a subscriber is connected
  wal_status,                              -- 'reserved' is healthy; 'lost' is bad
  pg_size_pretty(
    pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)
  ) AS lag
FROM pg_replication_slots
ORDER BY slot_name;
Watch wal_status If it ever shows lost, the source discarded WAL the target still needed and replication is broken — you must re-seed. Keep the target caught up, and consider a bounded max_slot_wal_keep_size only once you understand the trade-off.

3. On the TARGET: is the apply worker healthy?

psql — on TARGET 
-- live position of each subscription
SELECT subname, received_lsn, latest_end_lsn, last_msg_receipt_time
FROM pg_stat_subscription;

-- error counters: apply_error_count > 0 means the worker is hitting problems
SELECT subname, apply_error_count, sync_error_count
FROM pg_stat_subscription_stats;
What "caught up" looks like On the target pg_subscription_rel shows r for all tables, on the source the slot lag is 0 bytes during a write pause, and apply_error_count stays at 0. That is your green light to validate and cut over.
