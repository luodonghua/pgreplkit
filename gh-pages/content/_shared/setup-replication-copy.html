Set up replication — Replication Copy

This uses PostgreSQL's built-in initial copy: you create a publication on the source and a subscription on the target with copy_data = true. PostgreSQL loads all existing rows, then automatically switches to streaming live changes. It is version-independent (works across major versions) and works on every platform.

1 Create the publication on the SOURCE

The publication declares which tables to send.

If you chose "Specific tables"

psql — on SOURCE 
CREATE PUBLICATION pub_app
  FOR TABLE customers, orders
  WITH (publish = 'insert, update, delete, truncate');

If you chose "Entire schemas" (PostgreSQL 15+)

psql — on SOURCE (PG 15+) 
CREATE PUBLICATION pub_app
  FOR TABLES IN SCHEMA app
  WITH (publish = 'insert, update, delete, truncate');

Multiple schemas, and mixing schemas with individual tables

List several schemas separated by commas, and—on PG 15+—you can combine whole schemas with specific extra tables in the same publication:

psql — on SOURCE (PG 15+) 
-- several whole schemas at once
CREATE PUBLICATION pub_app
  FOR TABLES IN SCHEMA app, sales, inventory;

-- whole schemas PLUS one extra table from another schema
CREATE PUBLICATION pub_app
  FOR TABLES IN SCHEMA app, sales,
      TABLE public.audit_log;

Can I publish a whole schema but exclude a few tables?

There is no "exclude" clause PostgreSQL has no FOR TABLES IN SCHEMA app EXCEPT .... A schema publication always includes every current and future table in that schema. To publish most of a schema but omit a few tables, publish the tables you do want explicitly with FOR TABLE. This query builds that list for you (all tables in app except the ones you name):
psql — on SOURCE: generate the FOR TABLE list 
SELECT string_agg(format('%I.%I', schemaname, tablename), ', ' ORDER BY tablename)
FROM pg_tables
WHERE schemaname = 'app'
  AND tablename NOT IN ('temp_scratch', 'audit_big');   -- tables to EXCLUDE
-- copy the output into:
--   CREATE PUBLICATION pub_app FOR TABLE <paste list here>;
Because a schema publication auto-includes future tables too, an explicit FOR TABLE list is also what you want when you must be certain a specific table is never replicated — new tables won't sneak in.
On PostgreSQL 10–14 FOR TABLES IN SCHEMA does not exist. List the tables explicitly with FOR TABLE ..., or publish everything with FOR ALL TABLES.
A publication is just metadata — it defines what is available to subscribers. It does not move any data by itself.
2 Create the subscription on the TARGET

The subscription connects back to the source, creates a replication slot there, copies the existing rows, then streams changes.

psql — on TARGET, inside the replicated database 
CREATE SUBSCRIPTION sub_app
  CONNECTION 'host=SOURCE_HOST port=5432 user=repluser password=SECRET dbname=appdb'
  PUBLICATION pub_app
  WITH (
    copy_data    = true,     -- load existing rows first
    create_slot  = true,     -- create the slot on the source
    enabled      = true,     -- start immediately
    slot_name    = 'sub_app',
    disable_on_error = true   -- pause instead of retry-looping on a data error
  );
Because copy_data = true, PostgreSQL takes a consistent snapshot on the source, copies every existing row, and remembers the exact point to resume streaming from — so nothing is missed and nothing is applied twice.
Very large tables The initial copy reads the whole table under one snapshot and can take a long time on big data, keeping WAL on the source while it runs. If that is a concern and both sides are the same platform + major version, use a physical seed (RDS snapshot / Aurora clone) instead. Otherwise the pg_dump method lets you parallelize the load.
