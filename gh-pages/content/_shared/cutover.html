Cut over to the target

Cutover is the moment you move your application from the source to the target. Do it only when the target is fully caught up. The order below guarantees you lose no committed data.

1 Stop writes on the source

Put the application into maintenance mode, or revoke write access, so no new changes are made on the source. Reads can continue.

Until writes stop, the target is a moving target — there is always a little more data to apply. Stopping writes lets the stream drain to zero.
2 Wait for lag to reach zero
psql — on SOURCE 
SELECT slot_name,
       pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn) AS lag_bytes
FROM pg_replication_slots;
-- wait until lag_bytes = 0 for every slot
3 Sync sequences

Logical replication does not replicate sequence values (the "next id" counters). If you skip this, the target can hand out IDs that already exist and inserts will fail. Copy every sequence's current value from source to target:

bash — generate + apply setval statements 
# On the SOURCE: produce a script of setval() calls for all sequences
psql "host=SOURCE port=5432 user=repluser dbname=appdb" -Atc "
  SELECT format('SELECT setval(%L, %s, true);',
                schemaname||'.'||sequencename,
                last_value)
  FROM pg_sequences
  WHERE last_value IS NOT NULL;
" > sync_sequences.sql

# Apply it on the TARGET
psql "host=TARGET port=5432 user=repluser dbname=appdb" -f sync_sequences.sql
Sequences live outside the logical stream. Re-basing them on the source's current values prevents duplicate-key errors the first time the app writes to the target.
4 Validate

Confirm the two sides match before you commit to the switch.

bash — compare row counts per table 
for t in customers orders; do
  echo -n "$t  source="
  psql "host=SOURCE port=5432 user=repluser dbname=appdb" -Atc "SELECT count(*) FROM $t"
  echo -n "$t  target="
  psql "host=TARGET port=5432 user=repluser dbname=appdb" -Atc "SELECT count(*) FROM $t"
done

For stronger checks, compare per-table checksums (e.g. an aggregate over a hash of each row) rather than only counts.

5 Switch application traffic to the target

Repoint your application's connection string (or DNS / connection proxy) to the target and re-enable writes. The migration is complete.

Optional: rollback insurance (reverse replication) Before opening writes on the target, you can set up replication in the reverse direction (target → source) so the old source stays current and you can fall back to it. Keep the target quiesced while you wire the reverse direction, then open writes. See pgreplkit's reverse workflow for an automated version of this.
