Common prerequisites (all scenarios)

These apply regardless of platform. The version & platform-specific settings are in the table above; the items here are true for every logical-replication setup.

Configuration parameters to tune

Logical replication needs several server parameters set — some on the publisher, some on the subscriber. These follow the manual's Configuration Settings. On managed platforms you set them through the platform's mechanism (RDS/Aurora parameter groups, Cloud SQL/AlloyDB flags, Azure server parameters), and wal_level changes require a restart/reboot.

On the PUBLISHER (source)

ParameterSet toWhy
wal_levellogical Enables the extra WAL detail logical decoding needs. Static — requires a restart. On RDS/Aurora this is rds.logical_replication = 1 instead.
max_replication_slots ≥ number of subscriptions expected to connect, plus reserve for table sync Each subscription uses a slot on the publisher; table synchronization uses extra transient slots.
max_wal_senders ≥ max_replication_slots + number of physical replicas Each connected slot needs a WAL sender process; physical standbys need their own.

On the SUBSCRIBER (target)

ParameterSet toWhy
max_replication_slots ≥ number of subscriptions, plus reserve for table sync Used on the subscriber to track the origin/progress of each subscription (a different meaning than on the publisher).
max_logical_replication_workers ≥ number of subscriptions, plus reserve for table sync workers One apply worker per subscription, plus temporary workers that copy tables during the initial sync.
max_worker_processes ≥ max_logical_replication_workers + 1 Logical workers come from this pool, which is also shared with parallel queries and other extensions — size it with headroom.
Check what's set
psql — on each side 
-- publisher
SHOW wal_level;                       -- expect: logical
SHOW max_replication_slots;
SHOW max_wal_senders;
-- subscriber
SHOW max_replication_slots;
SHOW max_logical_replication_workers;
SHOW max_worker_processes;

Every replicated table needs a stable row identity

To replicate UPDATE and DELETE, PostgreSQL must be able to identify each row on the target. A primary key does this automatically. Tables without one need an explicit replica identity:

psql — on SOURCE, for tables without a PK 
-- Option A: a unique, NOT NULL index
ALTER TABLE my_table REPLICA IDENTITY USING INDEX my_unique_idx;

-- Option B: log the full old row (heavier, but always works)
ALTER TABLE my_table REPLICA IDENTITY FULL;
Without a replica identity, INSERTs still replicate but UPDATE/DELETE will error or be skipped, and your target silently drifts from the source.
A caveat with REPLICA IDENTITY FULL The manual notes that with REPLICA IDENTITY FULL, UPDATE/DELETE cannot be applied on the subscriber if the table has columns of a type with no default B-tree or hash operator class (e.g. point, box). Prefer a primary key or REPLICA IDENTITY USING INDEX for such tables.
This also blocks writes on the SOURCE — not just replication If a table is part of a publication that publishes updates/deletes but has no replica identity, PostgreSQL rejects the write on the publisher itself. Verified on PostgreSQL 16:
what your application hits on the SOURCE 
ERROR:  cannot update table "orders" because it does not have a replica identity and publishes updates
HINT:   To enable updating the table, set REPLICA IDENTITY using ALTER TABLE.
So the pre-flight check below isn't just about replication quality — skipping it can break your live application the moment it runs an UPDATE/DELETE.

Pre-flight check: find tables that will break UPDATE/DELETE

Run this on the source before you start. It lists every ordinary/partitioned table that has no usable row identity (replica identity default but no primary key, or replica identity nothing). Any table it returns needs a primary key or an explicit REPLICA IDENTITY first.

psql — on SOURCE (should return 0 rows before you proceed) 
SELECT n.nspname AS schema,
       c.relname AS "table",
       CASE c.relreplident
         WHEN 'd' THEN 'default (needs a PK)'
         WHEN 'n' THEN 'nothing'
       END AS replica_identity
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'p')                       -- ordinary + partitioned tables
  AND n.nspname NOT IN ('pg_catalog', 'information_schema')
  AND c.relreplident IN ('d', 'n')                  -- default or nothing
  AND NOT EXISTS (                                  -- ...and no primary key
        SELECT 1 FROM pg_index i
        WHERE i.indrelid = c.oid AND i.indisprimary)
ORDER BY 1, 2;
Tables with a primary key, a REPLICA IDENTITY USING INDEX, or REPLICA IDENTITY FULL are fine and won't appear. Only genuinely unsafe tables are listed, so an empty result means you're clear.

Planning: size & write-activity of the tables you'll replicate

Run this on the source before you set up replication to plan the move. Table/index sizes tell you how heavy the initial copy will be (and where a physical seed may be worth it); the DML rate (inserts/updates/deletes per second since the last stats reset) tells you how much change the stream must carry — useful for sizing the subscriber and predicting lag.

Scope it to a publication that already exists:

psql — on SOURCE (tables in publication 'pub_app') 
WITH db AS (   -- seconds since stats were last reset (DML counters are cumulative since then)
  SELECT GREATEST(EXTRACT(EPOCH FROM (now() - stats_reset)), 1) AS secs
  FROM pg_stat_database
  WHERE datname = current_database()
)
SELECT
  t.schemaname                                              AS schema,
  t.relname                                                 AS "table",
  t.n_live_tup                                              AS est_rows,
  pg_size_pretty(pg_table_size(c.oid))                      AS table_size,      -- heap + TOAST
  (SELECT count(*) FROM pg_index i WHERE i.indrelid = c.oid) AS idx_count,
  pg_size_pretty(pg_indexes_size(c.oid))                    AS indexes_size,
  pg_size_pretty(pg_total_relation_size(c.oid))             AS total_size,      -- heap + TOAST + indexes
  t.n_tup_ins AS inserts, t.n_tup_upd AS updates, t.n_tup_del AS deletes,
  round((t.n_tup_ins / db.secs)::numeric, 3)                AS ins_per_sec,
  round((t.n_tup_upd / db.secs)::numeric, 3)                AS upd_per_sec,
  round((t.n_tup_del / db.secs)::numeric, 3)                AS del_per_sec
FROM pg_stat_user_tables t
JOIN pg_class c ON c.oid = t.relid
CROSS JOIN db
WHERE (t.schemaname, t.relname) IN (
        SELECT schemaname, tablename
        FROM pg_publication_tables
        WHERE pubname = 'pub_app')
ORDER BY pg_total_relation_size(c.oid) DESC;

Planning before the publication exists? Scope by the schemas (or tables) you intend to publish instead — swap the WHERE clause for:

psql — scope by schema list 
WHERE t.schemaname IN ('app', 'sales', 'inventory')     -- schemas you plan to publish
-- ...or an explicit table list:
-- WHERE (t.schemaname, t.relname) IN (('app','customers'), ('app','orders'))

And a single roll-up for the whole scope (total size + combined DML rate):

psql — one-line summary of the replication scope 
WITH db AS (
  SELECT GREATEST(EXTRACT(EPOCH FROM (now() - stats_reset)), 1) AS secs
  FROM pg_stat_database WHERE datname = current_database()),
scope AS (
  SELECT c.oid, t.n_tup_ins, t.n_tup_upd, t.n_tup_del, t.n_live_tup
  FROM pg_stat_user_tables t
  JOIN pg_class c ON c.oid = t.relid
  WHERE (t.schemaname, t.relname) IN (
          SELECT schemaname, tablename FROM pg_publication_tables WHERE pubname = 'pub_app'))
SELECT count(*)                                          AS tables,
       sum(n_live_tup)                                   AS est_rows,
       pg_size_pretty(sum(pg_total_relation_size(oid)))  AS total_size,
       round((sum(n_tup_ins + n_tup_upd + n_tup_del) / max(db.secs))::numeric, 2) AS total_dml_per_sec
FROM scope CROSS JOIN db;
Reading the numbers est_rows and per-second rates come from the cumulative statistics views, so run ANALYZE first for fresh row estimates, and remember the counters are totals since the last stats reset — over a short window they can look inflated. For a true steady-state rate, note the values, wait a known interval, and compare. Big tables with high ins/upd/del_per_sec are the ones to watch for replication lag.

What logical replication does NOT replicate

These are silent gaps — plan for each one separately, or your target will be incomplete. This list follows the PostgreSQL manual's Restrictions.

Not replicatedWhat to do instead
Large objects (the lo / pg_largeobject interface) The manual is explicit: there is no workaround other than storing the data in normal tables. Move it to bytea columns (which are replicated), or migrate large objects separately with pg_dump -b.
Sequence values (the "next id" counters) The data in serial/identity columns replicates as table data, but the sequence itself stays at its start value on the subscriber. Sync sequences at cutover with setval() (see the cutover step).
DDL / schema changes (CREATE/ALTER/DROP) Apply the same DDL to both sides yourself; keep them coordinated for the life of the setup. Additive changes on the subscriber first avoids intermittent apply errors.
Views, materialized views, foreign tables Only tables (including partitioned tables) can be replicated; attempting others raises an error. Recreate/refresh these on the target.
Unlogged & temporary tables Their changes are not written to WAL, so nothing streams. Convert to a logged table (ALTER TABLE ... SET LOGGED) if the data must move.
TRUNCATE before PostgreSQL 11 Only replicated on PG 11+, and only when the publication includes truncate. Even then, mind foreign-key groups (see restrictions).
Partitioned tables By default replication originates from the leaf partitions, so the same partitions must exist on the subscriber. To replicate using the root table's identity instead, set publish_via_partition_root = true on the publication.
Check for large objects before you commit to a plan If this returns a non-zero count, part of your data lives in large objects that logical replication will not carry:
psql — on SOURCE 
SELECT count(*) AS large_object_count FROM pg_largeobject_metadata;

The target schema must exist before you subscribe

Logical replication copies data, not DDL. Tables (and their columns, types, and constraints) must already exist on the target. Create them from the source's schema:

bash — copy schema only (no data) 
pg_dump --schema-only \
  "host=SOURCE port=5432 user=repluser dbname=appdb" \
| psql "host=TARGET port=5432 user=repluser dbname=appdb"
Roles / globals pg_dump --schema-only does not include roles. If your objects are owned by specific roles, create those roles on the target first (e.g. with pg_dumpall --roles-only, editing out anything managed-platform-specific).

A dedicated replication user

Create a role specifically for the migration rather than reusing a superuser, where the platform allows it. It needs the REPLICATION capability (to create/read replication slots on the source) and SELECT on the tables being replicated. The subscriber connects to the source as this role, so create it on the source (publisher).

psql — on SOURCE: self-managed PostgreSQL 
-- 1. a login role with the REPLICATION attribute
CREATE ROLE repluser WITH LOGIN REPLICATION PASSWORD 'strong-secret';

-- 2. let it read the data it must replicate
GRANT USAGE ON SCHEMA app TO repluser;
GRANT SELECT ON ALL TABLES IN SCHEMA app TO repluser;
-- make the grant apply to tables created later, too
ALTER DEFAULT PRIVILEGES IN SCHEMA app GRANT SELECT ON TABLES TO repluser;

Then allow that role to connect for replication in pg_hba.conf (self-managed only) and reload:

pg_hba.conf — on SOURCE (adjust the subscriber CIDR) 
# TYPE  DATABASE  USER      ADDRESS            METHOD
host    appdb     repluser  10.0.0.0/24        scram-sha-256
# then:  SELECT pg_reload_conf();

Managed platforms grant REPLICATION through a role, not the attribute

On managed services you usually can't set the REPLICATION attribute directly; you grant a platform role instead. The connecting/admin user is the one shown in each platform's row of the version & prerequisites table above.

psql — on SOURCE: RDS / Aurora for PostgreSQL 
CREATE ROLE repluser WITH LOGIN PASSWORD 'strong-secret';
GRANT rds_replication TO repluser;                 -- RDS/Aurora replication privilege
GRANT USAGE ON SCHEMA app TO repluser;
GRANT SELECT ON ALL TABLES IN SCHEMA app TO repluser;
ALTER DEFAULT PRIVILEGES IN SCHEMA app GRANT SELECT ON TABLES TO repluser;
psql — on SOURCE: Cloud SQL / AlloyDB / Azure Flexible Server 
-- Cloud SQL / AlloyDB: connect as the admin (postgres / alloydbsuperuser) and grant REPLICATION
CREATE ROLE repluser WITH LOGIN REPLICATION PASSWORD 'strong-secret';
-- Azure Flexible Server: connect as the admin user, then
--   CREATE ROLE repluser WITH LOGIN PASSWORD 'strong-secret';
--   GRANT azure_pg_admin TO repluser;   -- or REPLICATION where permitted

GRANT USAGE ON SCHEMA app TO repluser;
GRANT SELECT ON ALL TABLES IN SCHEMA app TO repluser;
ALTER DEFAULT PRIVILEGES IN SCHEMA app GRANT SELECT ON TABLES TO repluser;
On the subscriber (target) The role that runs CREATE SUBSCRIPTION needs elevated rights: on PG 16+ grant it pg_create_subscription (plus CREATE on the database); on PG < 16 it must be a superuser (rds_superuser on RDS/Aurora). The exact target grant is in the prerequisites table above.
Always test in non-production first Run the whole flow end-to-end against a copy of your data before doing it for real. Logical replication is safe, but seeding mistakes and missing replica identities are easy to make and much cheaper to discover in a rehearsal.
