Overview

Bi-directional (active-active) replication means two nodes each publish and subscribe to the other, so a write on either node appears on both. Before PostgreSQL 16 this was dangerous: a replicated row would be re-published and echo back and forth forever (a replication loop). PostgreSQL 16 adds the subscription option origin = none, which tells a node "only send me changes that originated locally on your side, not rows you received from someone else." That single option makes safe two-node active-active possible with core logical replication.

Read this before you build active-active Active-active is powerful but shifts hard problems onto your application. Core logical replication does not resolve conflicts: if the same primary key is inserted or updated on both nodes, you get errors or divergence. It is a genuine fit only when writes are naturally partitioned (each node owns distinct keys/regions) or you have an application-level conflict strategy. For a one-way migration, do not use this — use a normal source→target scenario.

Prerequisites

  • PostgreSQL 16+ on both nodes. origin = none does not exist before 16. This is the hard requirement for loop-safe active-active.
  • wal_level = logical on both nodes (self-managed: postgresql.conf + restart; RDS/Aurora: rds.logical_replication = 1 in the parameter group + reboot).
  • Every replicated table needs a primary key (or explicit REPLICA IDENTITY). This is doubly important here because it is also how you avoid write conflicts.
  • Identical schema on both nodes (logical replication doesn't copy DDL). Keep schema changes coordinated for the life of the setup.
  • A conflict-avoidance design. The cleanest is non-overlapping key ranges — e.g. node A uses odd IDs / one set of regions, node B uses even IDs / another. This is what the example below uses.
  • Network reachability both ways on 5432: each node's subscriber must reach the other node's publisher.
Sequences will collide if shared If both nodes use the same sequence to generate IDs, they will both hand out 1, 2, 3, ... and immediately conflict. Use disjoint ranges: e.g. set different START/INCREMENT per node (node A odd, node B even), or UUID keys.

Set up active-active (origin = none)

The two nodes are symmetric. Below, Node A and Node B are the two servers; run each block on the node named in the label.

1 Create the schema on both nodes

Both nodes must have the same tables, each with a primary key.

psql — run on BOTH Node A and Node B 
CREATE TABLE items (
  id   bigint PRIMARY KEY,
  node text   NOT NULL,
  note text
);
2 Create a publication on each node
psql — on NODE A 
CREATE PUBLICATION pub_a FOR TABLE items;
psql — on NODE B 
CREATE PUBLICATION pub_b FOR TABLE items;
3 Create a subscription on each node with origin = none

Each node subscribes to the other. If both tables already hold data you must load it once out of band and use copy_data = false; if starting empty (recommended), either value is fine. Here both are empty, so we use copy_data = false.

psql — on NODE A (subscribes to B) 
CREATE SUBSCRIPTION sub_from_b
  CONNECTION 'host=NODE_B_HOST port=5432 user=repluser password=SECRET dbname=appdb'
  PUBLICATION pub_b
  WITH (copy_data = false, origin = none);
psql — on NODE B (subscribes to A) 
CREATE SUBSCRIPTION sub_from_a
  CONNECTION 'host=NODE_A_HOST port=5432 user=repluser password=SECRET dbname=appdb'
  PUBLICATION pub_a
  WITH (copy_data = false, origin = none);
origin = none is the whole trick. When Node A receives a row from Node B and applies it, that applied row has a non-local origin. Node A's publication would normally re-send it to B, creating an endless loop. With origin = none on B's subscription, B ignores anything that didn't originate on A — so replicated rows are never bounced back, and the loop is broken.
Seeding an existing dataset once If one node already has data and the other is empty, load a one-time copy first (e.g. set copy_data = true on only one of the two subscriptions, or seed with pg_dump), then keep the other at copy_data = false. Never let both subscriptions copy the same rows — that guarantees conflicts.

Verify there is no loop

Write to each node using its own key range, then confirm both converge and no row is duplicated or ping-ponging.

psql — write on each node (disjoint IDs) 
-- on NODE A (odd ids)
INSERT INTO items VALUES (1,'A','from-A'), (3,'A','from-A');
-- on NODE B (even ids)
INSERT INTO items VALUES (2,'B','from-B'), (4,'B','from-B');
psql — check on BOTH nodes (should be identical, 4 rows each) 
SELECT id, node FROM items ORDER BY id;
SELECT count(*) FROM items;   -- 4 on both nodes, and stays 4 (no loop growth)
What healthy looks like Both nodes show the same 4 rows and the count is stable. If the count kept climbing you'd have a loop — which is exactly what origin = none prevents.

Operating active-active safely

  • Conflicts are your responsibility. Watch pg_stat_subscription_stats.apply_error_count on both nodes. A rising count usually means a key collision — the two sides wrote the same PK. Fix the data and, if the worker is stuck, it will retry (or skip with ALTER SUBSCRIPTION ... SKIP for a known bad LSN).
  • Schema changes must be coordinated. Apply the same DDL to both nodes; logical replication does not carry DDL, and a mismatch breaks apply.
  • Sequences. Keep ID generation disjoint per node (odd/even increments or UUIDs) so the two sides never generate the same key.
  • This is two-node only. Core origin = none handles a pair cleanly. Meshes of three or more nodes are far more complex and are out of scope here.
